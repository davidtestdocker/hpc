# 單 L4：小型 causal LM 訓練與 CUDA profiling

2026-09-22，GKE `hpc-gpu-sg`，節點 `gke-hpc-gpu-sg-gpu-pool-9ad99345-81l2`。
本次補齊 Day 5／6 的小型語言模型效能實驗。使用 **13,003,776 parameters** 的
隨機初始化 causal LM 與本 repo README 文字快照，非 pretrained LLM fine-tuning。
9/21 synthetic Transformer 的模型、詞彙與目標不同，保留其原始結果，不能跨次比較提升率。

## 方法與可重現性

- PyTorch 2.12.0+cu126、CUDA runtime 12.6、driver 580.173.02、NVIDIA L4。
  `nvidia-smi` 顯示的 CUDA 13.0 是 driver 支援版本，並非本次 PyTorch runtime。
- 4 layers、hidden 512、8 heads、sequence 256、learned positional embeddings、
  causal attention mask、next-byte targets。字典為 256 個 UTF-8 byte；本文 tokens/s
  都是 **byte tokens/s**，不能直接與 BPE tokenizer 的 LLM tokens/s 比較。
- AdamW，lr 0.0003、dropout 0、BF16 autocast；每次重建相同 seed 20260922 的權重。
- corpus 快照與 SHA-256 一起保存；固定 128 個文字 windows、預先放入 GPU。
  排除讀檔、tokenizer、DataLoader、網路，量測 forward／loss／backward／optimizer。
- 一次初始 loss training step，20 warmup steps，再量 40 steps。每步結尾 CUDA
  synchronize；每種 batch 3 次，順序 **8、16、16、8、8、16**，不只挑最快的一次。
- timing 完成後另跑每組 5 steps 的 CPU／CUDA profiler，避免 profiler overhead
  混入 throughput。每秒約一次 `nvidia-smi` 記錄 utilization／memory／power／temperature。
- 因果性實測：改變位置 32 之後的 tokens，前 32 個位置 logits 最大差為 **0**。
  六次 final loss 均 finite；batch 8 為 5.688→2.570、batch 16 為 5.691→2.467。
  這只確認小資料訓練運作，未驗證泛化品質或等 token budget 收斂優劣。

## 未開 profiler 的結果

| Batch | Mean byte tokens/s | Mean step | Throughput CV | Max peak allocated |
|---:|---:|---:|---:|---:|
| 8 | 110,785 | 18.50 ms | 3.21% | 375.02 MiB |
| 16 | 200,841 | 20.39 ms | 0.42% | 532.39 MiB |

Batch 8→16：throughput **+81.29%**、step latency **+10.25%**、peak allocated
memory **+41.96%**。單步工作量加倍，因此 throughput 提升並非每步變快。
本次 batch 8 的三次範圍為 107,240～114,348；batch 16 為 199,914～201,588。
這是單次實驗中的三次重複，沒有跨日／跨機器的統計推廣。

## Profiling 如何解釋這個取捨

分析器只加總 raw trace 的 `cat=kernel, ph=X` 事件，避免 CPU operator、
record_function 與 GPU kernel 被重複加總。以下皆為 **五步 profiling** 的 CUDA
kernel duration sum，不能當 wall time、GPU utilization 或硬體峰值效率。

| Trace 觀察 | Batch 8 | Batch 16 |
|---|---:|---:|
| CUDA kernel events | 1,575 | 1,665 |
| 全部 kernel duration sum | 48.81 ms | 78.04 ms |
| 名稱包含 multi_tensor 的 kernel sum | 21.71 ms | 21.72 ms |
| 名稱包含 GEMM 的 kernel sum | 12.27 ms | 23.84 ms |

AdamW 相關的 multi-tensor kernels 在 batch 加倍後耗時幾乎不變，而 GEMM 總時間
接近加倍。這支持以下**推論**：此小模型包含明顯的每步固定 optimizer 成本；
較大 batch 把這些成本攤到更多 tokens，因而提高吞吐。不能只憑這份 trace 宣稱
整個 workload 已被證明是 memory-bound 或 compute-bound。

可供後續驗證的方向是 fused optimizer；本輪未實測，不把預期收益寫成成果。
面試時應先說測量與 tradeoff，再提出這個由 trace 支持的下一步假說。

Profiler 使用方式參照 [PyTorch 官方 profiler 文件](https://docs.pytorch.org/docs/2.14/profiler.html)；
實際 API 與 CUDA event capture 已在上述 2.12 runtime 驗證，並保存完整 trace。

## 限制

單張 L4 採 time-sharing；本次請求一個 share，不保證硬體隔離。啟動前 `nvidia-smi`
沒有其他 compute process，仍不能把共享設定描述為獨占 GPU。telemetry 是低頻採樣，
包含 setup／warmup／profile／trace export，不能把全程平均當作各 batch 的 GPU 使用率。
記憶體數字是 PyTorch peak allocated，與 reserved 或 nvidia-smi memory used 不同。

這是 13M 小型語言模型的受控訓練實驗，無 held-out dataset、生成品質、pretrained
LLM、multi-GPU scaling 或 RDMA 結論；也尚未接入 MPI API 的 benchmark dispatcher。
